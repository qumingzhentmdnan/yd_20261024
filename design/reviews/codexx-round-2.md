我接受这轮收敛：第一轮的 P1 应按“何时阻塞哪项工作”划分，不能把命名、候选协议和完整验收都设为同一道门槛。

**A．同意。**真正的 P1 是缺少唯一契约入口和采纳表。表中标明采纳、拒绝、后置，并统一 `/start` 的完成条件即可。纯更名无需全部升为 P1；只有名称背后存在生命周期或完成条件歧义时才阻塞开发。

**B．同意拆为两个门槛。**两小时 spike 只回答真实设备是否可用，完成 Hello、echo、基本关闭即可，不代表协议已验收。候选 schema、实例身份及失败语义确定后，内存 framing、fake 和双端候选实现可以提前并行。完整畸形帧、去重、取消竞态属于共同契约验收，在宣布协议稳定、依赖它独立交付前通过。我修正第一轮将“实现开工”和“验收通过”绑定过紧的建议。

**C．同意作为 MVP 硬限制。**一个 boot epoch 只允许一个顶层 Session；固定保存唯一启动记录，同 operationID、同参数返回已有状态或结果，同 ID 异参报错，其他启动一律拒绝。自然退出也不释放启动名额，并撤销 Gateway；guestd 重启使本次运行失效，由 Host 停 VM，重连不得复活授权。无需通用 LRU 或跨 daemon 恢复，但必须能识别 daemon 换代，不能只依赖仍未变化的 VM epoch。代价是瞬时故障也丢失运行连续性，不能同 VM 重跑，未取得快照时可能不可导出；保留 overlay 不构成恢复承诺。

**D．基本足够，符合两天范围。**正常停止按“撤销 Gateway→停止 Agent 并确认工作区写入者已终止→活 Guest 提取、Host 验证快照→停止 VM”。整个停止流程应有总时限，提取失败或超时继续停 VM。异常路径先隔离并停止，不等待导出。快照只有完整取回、校验通过才标记可导出；否则明确不可导出并保留 overlay。坚持的一点是：仅观察顶层 Agent 退出不足以证明工作区已静止，必须覆盖其子进程或写入进程组。

**E．同意，更适合 MVP。**持续读取并丢弃、固定有界 attachment 队列、溢出断 attachment，足以避免慢客户端拖死进程，无需重放环形缓冲。output gap 必须让用户可见；若拥塞连接无法送达通知，应在连接关闭原因或下次连接状态中呈现。SessionExited 与 EOF 分离，drain timeout 到期后明确输出可能截断。断 attachment 不终止 Session。

**F．同意，而且应尽早验证。**先选定一个拓扑供双端实现，但终端 echo 只证明连通。第一条端到端链路后，立即演示并发模型 SSE、终端持续输出与控制消息；让其中一路慢读，检查其他流仍能推进、取消和停止仍有界完成。两天内无需通用公平调度器，但必须排除全局写锁、共享无界队列造成的饥饿。

共识是用单次运行、失败即终止和允许输出丢失换取范围收敛；我坚持保留实例隔离、写入静止、内存有界和控制通道可推进这几条底线。

下一步最多五项交付物：

1. 唯一契约入口及采纳表，包含 VMInstance、Wait 和 `/start` 语义。
2. 单 Session 状态与撤权表，覆盖重试、自然退出、daemon 重启。
3. 候选拓扑与真实设备 Hello、echo、关闭演示。
4. 共同验收套件，覆盖 framing、去重、PTY 溢出及 SSE 并发控制。
5. 有总时限的停止与快照流程，明确可导出状态和失败结果。
